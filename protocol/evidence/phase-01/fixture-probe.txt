## Standing guard — does a reintroduced fixture row get refused?
  guard-shaped functions in monti/purge.py: NONE
  modules that both mention is_fixture and raise/abort: monti/__init__.py,
  monti/seed.py, monti/purge.py — checked individually rather than trusted:

    monti/__init__.py:100   the ONLY real guard. `flask launch` refuses to run if
                            any customer carries is_fixture = 1:
                              "Fixture rows are still present. Run `flask purge-fixtures`
                               first — launching on top of demo data is how a demo
                               customer reaches production."
                            It fires once, at launch, on one table.
    monti/seed.py           writes is_fixture = 1 deliberately; it is the seeder.
    monti/purge.py          deletes them and sweeps orphans. Not a guard.

  So the third clause of CHG-003's gate — "the guard fires on a deliberately
  reintroduced fixture row" — is met only for the launch command and only for the
  customers table. Nothing refuses a fixture row at write time, and 38 of the 45
  tables carry no is_fixture marker at all, so on those a fixture row is not even
  nameable. DATAOPS-01 owns SK-38 and calls this gate at Phase 2.
